# Issue 管理

このリポジトリでは、現在取り組むタスクと実装に向けた仕様を、`issues/` 直下の Markdown ファイルで管理する。

## Issue の選択と着手

- ユーザーが「次の issue」などを求めたら、`issues/` 直下の未完了 issue を確認し、候補を提示する。ユーザーが選ぶまで着手しない。
- 作業に着手する前に、内容に合った名前のブランチを作成して切り替える。

## Issue の作成と完了

- 既存の issue と重複するものは新規作成せず更新する。
- 仕様は issue で検討する。実装後はコードを仕様の正本とする。
- タスクの完了時には、コードから読み取れない設計判断や運用上の情報だけを文書に残し、issue ファイルを削除する。

## Issue ファイルの形式

- ファイル名は、日本時間の作成日時と内容が分かる短い題名をつなげた `YYYYMMDDHHmm-title.md` とする。題名に空白やファイル名に使えない文字を含めない。
- YAML frontmatter には `title`、`description`、`createdAt` を必ず記載する。`createdAt` は作成日時を `YYYY-MM-DDTHH:mm:ss+09:00` 形式で記載し、更新時も変更しない。
- 期限がある場合だけ、YAML frontmatter の `deadline` に `YYYY-MM-DD` 形式で記載する。
- 本文は次の見出しで構成する。
  - `## 目的`：この作業で実現することを簡潔に書く。
  - `## 仕様`：実装で満たす振る舞いや制約を書く。
  - `## TODO`：`- [ ]` または `- [x]` のチェック項目だけで書く。各項目は、作業内容と完了条件が分かるようにする。進捗はチェックの状態で示し、別の見出しや説明を設けない。
